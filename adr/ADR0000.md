# ADR0000: Project Foundation, Architecture Strategy & Roadmap Approach

## Status
Proposed (Pending User Review)

## Context
We need to build a robust, clean, and production-ready product modeled on Ninety (EOS edition) following the assessment specifications. The project must be easily understandable by junior developers (KISS - Keep It Simple, Stupid) while adhering to SOLID principles, feature-based clean architecture, clear error handling, and robust separation of concerns across Frontend, Backend, and Database.

In this ADR, we lay out:
1. The execution blueprint for the entire roadmap defined in `task_resources/task_todo_high_level.md`.
2. The core directory structure separating Frontend (`frontend/`), Backend (`backend/`), Database scripts, and Root orchestrators.
3. The design conventions for both Frontend and Backend (clean architecture, state management, API response envelope, script runners, and `HOW_TO_RUN.md`).

---

## 1. Roadmap Execution Strategy (ADR-Driven Progression)

Every step on the roadmap will follow this strict lifecycle:
1. **Author ADR document** (`adr/ADRXXXX.md`) detailing the exact technical design, schemas/contracts, and edge case handling.
2. **Review & Approval**: Run the ADR by the user for review before proceeding with implementation.
3. **Execution**: Implement the approved design (code, migrations, tests, runner scripts).
4. **Verification**: Execute tests and verify functionality. Update the roadmap status.

## 3. Backend Architectural Principles (FastAPI)

1. **Standardized Response Envelope**:
   Every API endpoint will return a consistent JSON contract:
   ```json
   {
     "code": 200,
     "message": "Success",
     "data": { ... }
   }
   ```
   On errors (HTTP 4xx, 5xx, or business validation failures):
   ```json
   {
     "code": 404,
     "message": "Resource not found",
     "data": null
   }
   ```
2. **Global Exception Handling**:
   - Centralized exception handlers in `app/main.py` intercept:
     - `HTTPException` (FastAPI standard)
     - `RequestValidationError` (Pydantic validation errors, mapped to 422 with readable field issues)
     - `SQLAlchemyError` / DB integrity errors (mapped cleanly to 400 or 500 without leaking raw database traces)
     - Uncaught generic exceptions (mapped to 500 internal server error)
3. **Clean Feature Separation (SOLID & KISS)**:
   - **Router (`api/v1/`)**: Pure HTTP handling, parameter extraction, returning envelopes.
   - **Service Layer (`services/`)**: Orchestrates business rules, transactions, and domain logic.
   - **Repository / Models (`models/` & `db/`)**: Data persistence and SQLAlchemy models.
   - **Domain Rules (`domain/`)**: Standalone pure functions (easy for junior devs to read and test without spinning up databases).

## 4. Frontend Architectural Principles (Next.js + TypeScript)

1. **Feature-Based Modular Structure**:
   - Code is grouped by business domain inside `src/features/<feature_name>/` (e.g., `scorecard`, `issues`, `meeting`).
   - Each feature has:
     - `components/`: UI presentation components.
     - `hooks/`: Custom state and data fetching hooks.
     - `services/`: API interaction methods using the standardized API client.
     - `types/`: Feature-specific TypeScript models.
2. **Robust State & Error Management**:
   - State handling across:
     - **Server State**: Managed via clear fetch hooks with explicit `{ data, isLoading, isError, error, refetch }` states.
     - **Network / Slow Connection Resilience**: Automatic request timeouts, retry hooks, and skeleton loaders/loading indicators for low-bandwidth connections.
     - **Optimistic UI Updates**: For inline score edits and To-Do toggles, updating UI immediately with rollback on server failure.
3. **Design System & Styling**:
   - Next.js App Router, Tailwind CSS, and shadcn/ui components for clean, accessible UI.

## 5. Execution Scripts & Runner Architecture

To ensure any developer or reviewer can run any layer independently without guessing commands:
- **`frontend/scripts/run_fe.sh`**: Installs dependencies (if needed) and launches Next.js dev server on port 3000.
- **`frontend/scripts/build_fe.sh`**: Runs TypeScript validation and Next.js production build.
- **`backend/scripts/run_be.sh`**: Sets up virtual environment / dependencies and starts FastAPI via Uvicorn on port 8000.
- **`backend/scripts/test_be.sh`**: Runs Pytest test suites.
- **`backend/scripts/seed_db.sh`**: Executes idempotent database seeder.
- **`HOW_TO_RUN.md`**: Comprehensive markdown guide documenting how to run the entire system via Docker Compose, as well as running Frontend, Backend, and PostgreSQL independently.

## 6. Security & Environment Protection (`.gitignore`)
All sensitive configuration files, environment variables (`.env`, `.env.local`, `.env.*`), virtual environments (`.venv`), temporary test artifacts, and build outputs (`.next/`, `node_modules/`, `__pycache__/`) must be strictly ignored by `.gitignore`. Only committed sample files like `.env.example` are kept in source control to guide onboarding safely.

## 7. Suggestions for User Review

We suggest including the following enhancements:
1. **Health Check Endpoints**: Provide `/health` and `/api/v1/health` in FastAPI to verify database connectivity.
2. **Interactive API Documentation**: Ensure FastAPI Swagger UI (`/docs`) and ReDoc (`/redoc`) are available and documented in `HOW_TO_RUN.md`.
3. **Mock/Fallback Mode for Frontend Dev**: Allow frontend developers to develop against seeded JSON mock structures if backend is offline.
4. **Environment Configuration Samples**: Provide `.env.example` files for both frontend and backend.
