# ADR0003: Database Seeding & Idempotent Migration Strategy (seed.json)

## Status
Accepted

## Context
Per the assessment specification (Sections 2.7 & Starter Files README):
- The starting state of the application comes from `seed.json` (located in `task_resources/seed.json`).
- Seed dataset contents:
  - 1 company (`co_1`, Acme Logistics, timezone `America/Chicago`).
  - 3 teams (`team_lead`, `team_sales`, `team_ops`).
  - 9 users across all three roles (`u1` through `u9`), with memberships across multiple teams.
  - 7 measurables with 13 weeks of scores (82 scores total), some sitting minutes from week boundaries.
  - 7 Q4 2026 Rocks and 12 Milestones.
  - 9 Issues (some direct, some linked to measurables + weeks; some solved with notes, some unsolved).
  - 19 To-Dos (some direct, some linked to source issues; some completed, some overdue, some pending).
  - 2 ended Level 10 meetings (`mt1` and `mt2`) with attendee lists and ratings.
- **Critical Requirements**:
  1. **Exact IDs**: All primary key IDs (`u1`, `m1`, `r1`, `t10`, `mt1`, `team_lead`, etc.) from `seed.json` must be strictly preserved.
  2. **Idempotency**: Running the seed script multiple times or restarting Docker Compose must be completely safe, duplicate-free, and idempotent.
  3. **Foreign Key Dependency Order**: Records must be inserted in proper relational order to respect foreign key constraints.
  4. **Executable Runner Script**: A standalone script `backend/scripts/seed_db.sh` must execute the seeder.

---

## 1. Technical Strategy

### 1.1 Seeding Pipeline (`backend/app/db/seed.py`)
We will create a structured, typed seeder module using SQLAlchemy 2.0:
1. **JSON Parsing & Validation**: Read `seed.json` from `task_resources/seed.json` (or configured seed file path) using Pydantic validation schemas.
2. **Relational Ingestion Sequence**:
   - `Company` $\rightarrow$ `co_1`
   - `Teams` $\rightarrow$ `team_lead`, `team_sales`, `team_ops`
   - `Users` $\rightarrow$ `u1` .. `u9`
   - `TeamMemberships` $\rightarrow$ User-Team pairs
   - `Measurables` $\rightarrow$ `m1` .. `m7` (handling goal types: `at_least`, `at_most`, `between`, `exactly`)
   - `Scores` $\rightarrow$ Measurable scores by `week_start`
   - `Rocks` $\rightarrow$ `r1` .. `r7`
   - `Milestones` $\rightarrow$ `ms1` .. `ms12`
   - `Issues` $\rightarrow$ `i1` .. `i9` (mapping `source.measurable_id` and `source.week_start`)
   - `Todos` $\rightarrow$ `t1` .. `t41` (mapping `source_issue_id`)
   - `Meetings` $\rightarrow$ `mt1`, `mt2` (with attendees and ratings)
3. **Idempotency Implementation**:
   - For every entity, we utilize an **Upsert / Merge** pattern:
     - Check if record exists by primary key (or composite unique keys for memberships/scores/ratings).
     - If it exists, update attributes; if not, insert.
   - Alternatively, support a `--reset` flag that cleanly truncates/resets tables and reloads fresh data.

### 1.2 CLI & Runner Scripts
- `backend/app/db/seed.py`: Can be run as a Python CLI module:
  `python -m app.db.seed [--reset]`
- `backend/scripts/seed_db.sh`:
  Bash script that activates the virtual environment and runs `python -m app.db.seed`.
- Update `scripts/start_all.sh` to automatically run `seed_db.sh` after applying migrations, ensuring the app is always seeded and ready on startup.

---

## 2. Verification & Testing Strategy
- Unit test in `backend/tests/test_seed.py`:
  1. Execute `seed_db()` against an empty test database session.
  2. Verify all record counts match `seed.json` exactly:
     - 1 Company, 3 Teams, 9 Users, 11 Memberships
     - 7 Measurables, 82 Scores
     - 7 Rocks, 12 Milestones
     - 9 Issues, 19 To-Dos
     - 2 Meetings, 10 Meeting Attendees, 7 Ratings
  3. Execute `seed_db()` a second time on the same session to prove idempotency (no duplicates, no constraint errors, exact same counts).
