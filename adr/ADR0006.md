# ADR0006: Server-Side Authorization & Role-Based Access Control (RBAC)

## Status
Accepted

## Context
Per Sections 2.4, 2.5, and 2.7 of the assessment specification:
> *"Each user has one company-wide role and belongs to one or more teams."*
> *"Authorization: every role rule in 2.4 is enforced on the server. Hiding a button is not authorization."*
> *"A team the user can't access returns an error, even by guessed ID."*
> *"API tests: A Team Member reading another team's data is refused. An Observer write is refused."*

### Role Matrix (Section 2.4):
| Role | Capabilities |
| :--- | :--- |
| **Admin** (`u1`) | Everything a Team Member can, in **every team** across the company. |
| **Team Member** (`u2`-`u4`, `u6`, `u8`, `u9`) | Read and change data **in their own teams only**. Start, facilitate, and rate meetings. Own Measurables, Rocks, To-Dos, and Issues. |
| **Observer** (`u5`, `u7`) | Read data **in their own teams only** and join meetings. **Cannot** change data, facilitate, rate, or own anything. |

### Out of Scope:
- Sign-up or password-based auth: A seeded user switcher (simulated via an `X-User-Id` request header) is explicitly sufficient.

## 1. Technical Design

### 1.1 User Context & Dependency Injection (`app/api/deps.py`)
We will create reusable FastAPI dependencies with zero external authentication libraries:
```python
def get_current_user(
    x_user_id: Optional[str] = Header(None, alias="X-User-Id"),
    db: Session = Depends(get_db)
) -> User:
    ...
```
- Reads the `X-User-Id` header (defaulting to `u1` if omitted in development/testing).
- Fetches the `User` from the database. If invalid, raises `HTTP 401 Unauthorized` with our standard envelope (`{"code": 401, "message": "Invalid or missing user context", "data": null}`).

### 1.2 Team Boundary & Permission Verifiers
We will provide clean, declarative permission dependencies:
1. `require_team_access(team_id: str, write: bool = False)`:
   - Verifies the user has rights to the specified `team_id`:
     - If user is `Admin` $\rightarrow$ Allowed for any team in their company.
     - If user is `Team Member`:
       - User must belong to `team_id` in `team_memberships`. If not $\rightarrow$ `HTTP 403 Forbidden` (`"Access to this team is denied"`).
       - Allowed for both read and write.
     - If user is `Observer`:
       - User must belong to `team_id` in `team_memberships`. If not $\rightarrow$ `HTTP 403 Forbidden`.
       - If `write=True` $\rightarrow$ `HTTP 403 Forbidden` (`"Observers have read-only access and cannot perform modifications"`).
2. `require_facilitator_or_admin(meeting: Meeting, user: User)`:
   - For advancing meeting sections or concluding: Only the meeting's facilitator (or company Admin) is permitted.
3. `require_meeting_rater(meeting: Meeting, user: User)`:
   - Only attending Admins and Team Members can submit ratings (Observers cannot rate).

## 2. Testing Strategy (`backend/tests/test_rbac.py`)
We will author a dedicated integration test suite verifying every RBAC boundary:
1. **Cross-Team Access Rejection**:
   - `u6` (`team_member` of `team_sales` only) attempts to read `team_ops` $\rightarrow$ `HTTP 403`.
   - `u6` attempts to read an unassigned or non-existent/guessed team ID $\rightarrow$ `HTTP 403` / `HTTP 404`.
2. **Observer Write Rejection**:
   - `u5` (`observer` of `team_lead`) attempts to edit a score, create an issue, solve an issue, mark a todo done, or submit a meeting rating $\rightarrow$ `HTTP 403`.
   - `u5` reading `team_lead` data $\rightarrow$ `HTTP 200` (Read-only allowed).
3. **Admin Global Access**:
   - `u1` (`admin`) reads and writes to `team_sales` and `team_ops` (even though not explicitly seeded as a team member of those teams) $\rightarrow$ `HTTP 200`.
4. **Ownership Rules**:
   - Observers cannot own Measurables, Rocks, Issues, or To-Dos.
