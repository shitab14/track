# ADR0007: Core REST API Design & CRUD Endpoints

**Status:** Approved  
**Branch:** development  
**Author:** AI Assistant  
**Date:** 2026-11-25

---

## Context

ADR0006 established the RBAC layer (`deps.py`): `get_current_user`, `require_team_read`, and `require_team_write`. The DB schema (ADR0001), domain rules (ADR0004), and seeding (ADR0003) are all in place. This ADR defines the full REST API surface needed to power the Team Page (Section 2.1–2.5 of the brief) plus a Teams listing endpoint used by the user switcher.

All responses follow the envelope convention: `{"code": <int>, "message": "<str>", "data": <payload | null>}`.

---

## Decision

### 1. File Layout

New files introduced by this ADR:

```
backend/app/
  services/
    __init__.py
    scorecard.py         # scorecard query + score upsert
    issues.py            # issue CRUD + solve + make-issue
    todos.py             # todo CRUD + done/undo
    rocks.py             # rocks + milestones read
    teams.py             # team list
  api/v1/
    teams.py             # GET /teams, GET /teams/{id}/...
    scores.py            # POST /scores/{id}/make-issue (ADR0008 guard here too)
    issues.py            # issue endpoints
    todos.py             # todo endpoints
    rocks.py             # rocks endpoints
  schemas/
    __init__.py
    common.py            # ApiResponse[T], Paginated
    scorecard.py
    issue.py
    todo.py
    rock.py
    team.py
```

`router.py` gains five new sub-routers.

### 2. Service Layer Pattern

Each service module receives `db: Session`, `team: Team`, and `current_user: User` from the router. The service calls `app.domain.rules` for computed fields and `app.core.clock` for date logic. No business rules live in routers or schemas.

### 3. Endpoints

#### 3.1 Teams

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/api/v1/teams` | read | List teams accessible to current user. Admin = all teams; others = their memberships only. |

**Response `data`:**
```json
[
  { "id": "t1", "name": "Leadership", "user_role": "admin" }
]
```

#### 3.2 Scorecard

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/api/v1/teams/{team_id}/scorecard` | read | 13-week scorecard grid for all team measurables. |
| `POST` | `/api/v1/teams/{team_id}/scores` | write | Upsert a score (measurable_id + week_start). |

**GET Scorecard `data`:**
```json
{
  "weeks": ["2026-08-18", ..., "2026-11-09"],
  "measurables": [
    {
      "id": "m1",
      "name": "Revenue",
      "unit": "$",
      "goal_type": "at_least",
      "goal_value": 50000,
      "goal_min": null,
      "goal_max": null,
      "owner": { "id": "u1", "name": "Alice" },
      "scores": {
        "2026-11-09": { "id": 42, "value": 55000, "status": "on_track" },
        "2026-11-02": { "id": 41, "value": 44000, "status": "off_track" }
      },
      "current_week_score": null
    }
  ]
}
```

- Weeks are Monday dates in `America/Chicago` for the 13-week window ending at `get_last_closed_week_start()`. Current (open) week is excluded from the grid but `current_week_score` is included separately for display.
- Status is derived by `compute_measurable_status()` from `app.domain.rules`.
- Missing scores produce no key in the `scores` dict (frontend renders blank cell).

**POST `/teams/{team_id}/scores` body:**
```json
{ "measurable_id": "m1", "week_start": "2026-11-09", "value": 55000 }
```
- Upserts via `INSERT ... ON CONFLICT DO UPDATE` (or SQLAlchemy merge).
- Returns the updated score with computed status.
- `week_start` must be a Monday; server validates or rejects with `422`.
- Scores for future weeks beyond today are rejected with `422`.

#### 3.3 Issues

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/api/v1/teams/{team_id}/issues` | read | Unsolved issues (EOS-ordered) + solved issues (most recent first). |
| `POST` | `/api/v1/teams/{team_id}/issues` | write | Create a new issue. |
| `PATCH` | `/api/v1/issues/{issue_id}/priority` | write (team) | Update priority (1–5 or null). |
| `POST` | `/api/v1/issues/{issue_id}/solve` | write (team) | Solve issue — `resolution_note` required. |
| `POST` | `/api/v1/scores/{score_id}/make-issue` | write (team) | Idempotently promote a score to an issue. Concurrency-safe. |

**GET Issues `data`:**
```json
{
  "unsolved": [
    {
      "id": "i1", "title": "...", "priority": 5,
      "owner": { "id": "u2", "name": "Bob" },
      "source": { "measurable_id": "m1", "week_start": "2026-11-02" },
      "created_at": "2026-10-01T10:00:00Z"
    }
  ],
  "solved": [
    {
      "id": "i5", "title": "...", "priority": null,
      "resolution_note": "Fixed",
      "solved_at": "2026-11-10T14:00:00Z"
    }
  ]
}
```
- Unsolved ordering via `sort_issues()` from `app.domain.rules`.

**POST `/teams/{team_id}/issues` body:**
```json
{ "title": "Cash flow gap", "priority": 3 }
```
- `title` required; `priority` optional (null = no priority, sorts last).
- `owner_id` = `current_user.id`.

**PATCH `/issues/{issue_id}/priority` body:**
```json
{ "priority": 4 }
```
- `priority` nullable integer 1–5.
- Verifies team membership via `require_team_write` on the issue's team.

**POST `/issues/{issue_id}/solve` body:**
```json
{ "resolution_note": "Resolved by increasing budget." }
```
- Sets `solved_at = now_utc`, stores `resolution_note`.
- Returns `422` if already solved.

**POST `/scores/{score_id}/make-issue`** (no body)  
- Looks up the score → determines measurable_id + week_start.
- Attempts INSERT into issues. If `IntegrityError` from `uq_unsolved_source_issue`, catches and returns existing issue instead (HTTP 200 with `code: 200`).
- Full idempotency/concurrency design is formalized in ADR0008 but guarded here.

#### 3.4 To-Dos

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/api/v1/teams/{team_id}/todos` | read | All todos with computed overdue flag. |
| `POST` | `/api/v1/issues/{issue_id}/todos` | write (team) | Create todo linked to an issue. |
| `POST` | `/api/v1/todos/{todo_id}/done` | write (team) | Mark done. |
| `POST` | `/api/v1/todos/{todo_id}/undo` | write (team) | Clear done status. |

**GET Todos `data`:**
```json
{
  "completion_rate": 0.75,
  "todos": [
    {
      "id": "td1", "title": "Call supplier",
      "owner": { "id": "u2", "name": "Bob" },
      "due_date": "2026-11-15",
      "done": false, "overdue": true,
      "source_issue_id": "i1",
      "created_at": "..."
    }
  ]
}
```
- `overdue` = `is_overdue(due_date)` from `app.core.clock`.
- `completion_rate` = `compute_todo_completion_rate(todos)` from `app.domain.rules`.

**POST `/issues/{issue_id}/todos` body:**
```json
{ "title": "Follow up with vendor", "owner_id": "u3" }
```
- `due_date` defaults to `get_today_company() + 7 days`.
- `owner_id` optional — defaults to `current_user.id`.

**POST `/todos/{todo_id}/done`** / **POST `/todos/{todo_id}/undo`** (no body)  
- Sets / clears `done_at`. Returns updated todo.

#### 3.5 Rocks

| Method | Path | Auth | Description |
|--------|------|------|-------------|
| `GET` | `/api/v1/teams/{team_id}/rocks` | read | All rocks with milestones, computed status, progress. |

**GET Rocks `data`:**
```json
[
  {
    "id": "r1", "title": "Launch new product",
    "quarter": "Q4-2026", "owner": { "id": "u2", "name": "Bob" },
    "computed_status": "on_track",
    "progress": { "done": 2, "total": 4 },
    "milestones": [
      { "id": "ms1", "title": "Design complete", "due_date": "2026-10-15", "done": true, "overdue": false },
      { "id": "ms2", "title": "Dev complete", "due_date": "2026-11-30", "done": false, "overdue": false }
    ]
  }
]
```
- `computed_status` and `progress` via `compute_rock_status_and_progress()` from `app.domain.rules`.

### 4. Shared Schemas (`app/schemas/`)

All routers use Pydantic v2 `model_config = ConfigDict(from_attributes=True)` for ORM compatibility. `ApiResponse[T]` is a generic wrapper:

```python
class ApiResponse(BaseModel, Generic[T]):
    code: int
    message: str
    data: Optional[T] = None
```

Schemas are thin — no business logic. All derived fields (status, overdue, etc.) are injected by the service layer before schema construction.

### 5. Error Conventions

| Scenario | HTTP | code | message |
|----------|------|------|---------|
| Team not found | 404 | 404 | "Team not found" |
| Access denied | 403 | 403 | "Access denied" |
| Resource not found | 404 | 404 | "Not found" |
| Validation error | 422 | 422 | FastAPI default detail |
| Already solved | 409 | 409 | "Issue already solved" |
| Duplicate make-issue | 200 | 200 | "Issue already exists" |

### 6. Routing Registration

`router.py` will include:
```python
api_router.include_router(teams_router, prefix="/teams", tags=["Teams"])
api_router.include_router(scores_router, prefix="", tags=["Scores"])
api_router.include_router(issues_router, prefix="", tags=["Issues"])
api_router.include_router(todos_router, prefix="", tags=["Todos"])
api_router.include_router(rocks_router, prefix="", tags=["Rocks"])
```

---

## Consequences

**Positive:**
- Thin routers, services hold all query logic, domain module holds all rules — clean arch enforced.
- Generic `ApiResponse[T]` schema eliminates boilerplate response wrapping.
- Concurrency guard for "Make it an Issue" colocated with the endpoint (ADR0008 formalises the full story).
- All endpoints are RBAC-protected via existing `deps.py` — zero new auth code needed.

**Negative / Trade-offs:**
- `GET /teams` has no pagination (at most 3 teams in seed; acceptable for scope).
- No score deletion endpoint — out of scope for assessment.
- `PATCH` used for priority update (not `PUT`) since only one field changes.
