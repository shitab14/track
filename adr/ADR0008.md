# ADR0008: Concurrency and Idempotency for “Make it an Issue”

## Status
Accepted

## Context
The scorecard API lets a user promote a score to an Issue. A score is identified by its measurable and Monday `week_start`. Repeated clicks, retries after a timeout, or simultaneous requests must not create multiple unsolved Issues for the same measurable and week.

Ordinary application-level check-then-insert logic is insufficient: two requests can both observe that no Issue exists before either commits. The schema already defines a partial unique index named `uq_unsolved_source_issue` on `(source_measurable_id, source_week_start)` for rows with a non-null source measurable and `solved_at IS NULL`. The ADR0007 service first checks for an existing row, then inserts, and catches `IntegrityError` to load and return the winning row.

## Decision

1. **The database is the concurrency authority.** Keep the partial unique index as the invariant. It allows historical solved Issues for the same source week, while at most one matching Issue may remain unsolved. Issues without scorecard provenance are not covered by this uniqueness rule.
2. **Keep the endpoint idempotent.** `POST /api/v1/scores/{score_id}/make-issue` resolves the score to its measurable and week. If an unsolved source Issue already exists, return it. Otherwise attempt to insert and commit.
3. **Recover from the losing concurrent insert.** On an integrity conflict, roll back the failed transaction, query the unique key again, and return the existing Issue with HTTP 200 and the standard response envelope. Re-raise the original error if no matching Issue exists, since that indicates a different integrity failure.
4. **Preserve authorization and ownership.** Resolve the score, enforce read access to its team before disclosing its existence, then enforce write access before creating or returning the promoted Issue. The first successful request’s user remains the Issue owner; later retries do not alter the Issue.
5. **No extra idempotency-key table or locking protocol.** The natural key and database constraint fully express the desired behavior. Keep the path portable across PostgreSQL and SQLite test databases using the existing dialect-specific partial-index predicates.

## API behavior

- First successful promotion: HTTP 200, message `Issue created`, Issue payload.
- Repeat or concurrent losing promotion: HTTP 200, message `Issue already exists`, same Issue payload.
- Unknown score: HTTP 404.
- User without team write permission: HTTP 403.

The endpoint creates the Issue title from the measurable name and score week. A score does not need to be off-track at request time; the API operation explicitly requests promotion, and UI eligibility can be based on the scorecard status.

## Consequences

- The database constraint, rather than request timing, guarantees no duplicate unsolved source Issues.
- The application handles expected uniqueness conflicts as successful idempotent requests.
- Once an Issue is solved, a later promotion for that score may create a new unsolved Issue, retaining the solved record as history.
- The existing rule is scoped to measurable/week, not team, because a measurable belongs to exactly one team.

## Verification

Execution should include tests for sequential repeat requests, two concurrent requests, solved-source re-promotion, and cross-team/observer authorization. The concurrency test must assert one unsolved Issue exists and all successful callers receive its ID. Run these against the production PostgreSQL dialect where available; SQLite coverage alone does not prove PostgreSQL transaction behavior.
