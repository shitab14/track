# ADR0009: Real-Time Sync & Level 10 Meeting State Machine

## Status
Accepted

## Context

The Meeting page runs a live Level 10 Meeting that every attendee watches from
their own browser. Section 2.5 requires that everyone sees the same section and
timer, that changes reach all attendees within about a second, that the server
owns the timer, that an overrun section shows as *over time* without
auto-advancing, and that late joins, refreshes and reconnects (facilitator
included) receive the current state. Section 2.8 asks us to choose the
real-time transport and explain how meeting state is owned and recovered.

The schema from ADR0001 already models this: `meetings` carries
`current_section` (`scorecard | ids | conclude | ended`), `section_started_at`,
`started_at`, `ended_at`, `facilitator_id`, and a **partial unique index
(`uq_active_team_meeting`) enforcing one active meeting per team**.
`meeting_attendees` and `meeting_ratings` (1–10, upsertable) are also present.
No meeting service or endpoints exist yet. Authorization runs through the
`X-User-Id` header and the `require_team_read` / `require_team_write`
dependencies from ADR0006.

Two distinct notions of "now" coexist and must not be confused:
- **Business clock (`APP_NOW`, frozen at `2026-11-11T15:00:00Z`)** drives domain
  rules — weeks, overdue, the last closed week shown on the Scorecard.
- **Meeting wall clock (real UTC `now()`)** drives the live meeting timer.
  Section elapsed time must advance in real seconds, so it cannot read the
  frozen `APP_NOW`.

## Decision

### 1. Transport: Server-Sent Events (SSE), actions stay REST
The only thing that must be *pushed* is server→client state. All client intents
(start, advance, end, rate, edit a score, make an issue, toggle a To-Do) are
ordinary authenticated REST calls that already exist or are added here. We
therefore use **SSE over a native Starlette `StreamingResponse`** for the
push channel and keep writes on REST.

Rationale versus WebSockets: SSE is one-directional (server→client), which is
exactly the shape of this problem; it rides plain HTTP, reconnects
automatically in the browser's `EventSource`, and needs **no extra library**
(RULE.md zero-bloat). WebSockets would add a bidirectional channel we do not
need, plus duplicated action paths and connection bookkeeping. The tradeoff —
SSE cannot carry custom request headers from the browser — is handled in
decision 6.

### 2. The database Meeting row is the single source of truth
Live state is not held in memory. `current_section` and `section_started_at`
on the `meetings` row define the authoritative state; the in-process pub/sub
layer (decision 4) only *notifies* subscribers that they should read it. A
server restart loses no meeting state, and any node can answer "what is the
current state" from the row alone. This is what makes recovery trivial
(decision 5).

### 3. State machine (server-enforced)
Linear sections with the seeded durations, advanced only forward:

```
scorecard (5m) --advance--> ids (60m) --advance--> conclude (10m) --advance--> ended
         any state ------------------- end -------------------------> ended
```

- **Start** (`Admin`/`Team Member`): creates the meeting, sets
  `current_section = scorecard`, `section_started_at = now()`, and makes the
  caller the facilitator. The `uq_active_team_meeting` index guarantees one
  active meeting per team; a concurrent second start catches `IntegrityError`
  and returns the existing active meeting (same idempotent pattern as ADR0008).
- **Advance / End**: facilitator only (`403` otherwise). Advance is applied
  under a row lock (`SELECT … FOR UPDATE`) and transitions strictly by the
  current section, so a double-click cannot skip a section. Reaching/ending at
  `ended` sets `ended_at` and `current_section = ended`; an already-ended
  meeting rejects further transitions (`409`).
- **Timer & overrun**: the server never auto-advances. Elapsed is
  `wall_now − section_started_at`; a section past its budget is reported with
  `over_time = true`. The facilitator may advance or end at any time,
  before or after the budget.

### 4. Broadcast: in-process async pub/sub
A module-level broadcaster keeps, per `meeting_id`, a set of `asyncio.Queue`
subscribers. Each mutating action publishes one event to that meeting's queues
after its transaction commits. Built only on `asyncio` + Starlette — no broker.

**Single-process assumption:** this works for one Uvicorn worker, which is how
`docker compose up` runs the stack for this assessment. Horizontal scaling
(multiple workers/nodes) would require a shared bus; **Postgres
`LISTEN/NOTIFY`** is the natural drop-in since we already depend on Postgres,
and the publish call is the only seam that would change. This limitation is
recorded here and will be noted in the README.

### 5. Recovery via snapshot-on-connect
The SSE endpoint, immediately on connect, sends the full current state
snapshot, then streams subsequent change events. Late joiners, refreshes and
reconnects (facilitator included) therefore converge on the current state with
no special handling — the first event they receive *is* the truth. The
browser's `EventSource` auto-reconnects on a dropped connection and re-runs this
path. A periodic heartbeat (SSE comment every ~15s) keeps proxies from idling
the connection and provides a liveness signal.

### 6. Authorization of the stream
The SSE endpoint re-uses the seeded-user model but takes the user id as a
**query parameter** (`?user_id=`) because `EventSource` cannot set the
`X-User-Id` header. The handler resolves the user exactly as `get_current_user`
does and enforces `require_team_read` on the meeting's team before opening the
stream; a non-member (even with a guessed meeting id) is refused. All mutating
endpoints keep header-based auth. Role rules: read-team users may subscribe and
join; only `Admin`/`Team Member` may start, advance, end or rate; Observers are
read-only and are excluded from rating.

### 7. Event payloads: state snapshot + thin change signals
Two event types over the stream:
- **`meeting_state`** — the authoritative snapshot: `section`,
  `section_started_at`, `server_now` (so clients compute clock offset and render
  the countdown locally between pushes), `over_time`, `facilitator_id`,
  `attendees`, `ratings` summary, `ended_at`.
- **`data_changed`** — a thin signal (`{scope: "scorecard" | "issues" |
  "todos"}`) telling clients to refetch that section from its existing REST
  endpoint.

Sending change *signals* rather than full domain payloads keeps the stream
small and, crucially, keeps all business-rule computation in the REST/service
layer that ADR0004–0007 already built and tested — the stream never
recomputes statuses.

### 8. No schema change
Everything needed exists in the ADR0001 tables. ADR0009 adds a
`services/meetings.py`, a `api/v1/meetings.py` router, and the SSE broadcaster;
it introduces no migration.

## API surface (new)

| Method & path | Auth | Purpose |
| --- | --- | --- |
| `POST /teams/{team_id}/meetings` | team write | Start a meeting; become facilitator (idempotent on active meeting) |
| `GET /teams/{team_id}/active-meeting` | team read | Discover the team's current active meeting (for Join) |
| `GET /meetings/{meeting_id}` | team read | One-shot current state snapshot |
| `GET /meetings/{meeting_id}/events?user_id=` | team read | SSE stream: snapshot-on-connect, then live events |
| `POST /meetings/{meeting_id}/join` | team read | Record attendee (idempotent) |
| `POST /meetings/{meeting_id}/advance` | facilitator | Advance to the next section |
| `POST /meetings/{meeting_id}/end` | facilitator | End the meeting |
| `PUT /meetings/{meeting_id}/rating` | attending Admin/Team Member | Set or change own rating (1–10) |

All responses use the standard `{code, message, data}` envelope. The meeting
**summary** endpoint and the strategy for keeping past summaries immutable after
later edits are deliberately **out of scope here and owned by ADR0010**.

## Consequences

- Real-time delivery needs no broker and no new dependency; the whole push path
  is `asyncio` + Starlette + the existing Postgres row.
- Because state lives in the row and the snapshot is sent on connect, every
  recovery case (late join, refresh, reconnect, facilitator reconnect) is one
  code path.
- The server owning `section_started_at` plus `server_now` lets clients render a
  smooth per-second countdown without the server pushing every tick.
- The in-process broadcaster is correct for a single worker only; multi-worker
  deployment is a documented follow-up (Postgres `LISTEN/NOTIFY`).
- Keeping actions on REST means the stream carries no authorization-sensitive
  mutations and reuses the already-tested service layer for every computed value.

## Verification

Execution (next stage) should include:
- **State-machine unit tests** (service layer): legal transitions, double-advance
  under lock does not skip a section, non-facilitator advance/end refused,
  start is idempotent per team, end is terminal.
- **Authorization tests**: non-member cannot open the stream or join; Observer
  cannot start/advance/rate; rating range and upsert behavior.
- **SSE integration test**: a streaming client receives the snapshot on connect
  and a subsequent `meeting_state` event after the facilitator advances, within
  the ~1s budget; `over_time` flips once a section budget elapses (test with a
  shortened budget / injected clock).
- The **two-browser Playwright** proof of live sync is owned by ADR0012/0013 and
  will consume this transport; it is referenced, not duplicated, here.

## Stage 1 Review: Questions for User

1. **SSE vs WebSockets.** This ADR chooses SSE (server→client only, actions stay
   REST, no new dependency). Approve SSE, or do you want a bidirectional
   WebSocket channel instead (e.g. to showcase it in the walkthrough)?
2. **Stream authorization via query param.** Because `EventSource` cannot send
   the `X-User-Id` header, the SSE endpoint takes `?user_id=` and enforces the
   same `require_team_read` check. Accept this deviation, or prefer a
   cookie-based scheme for the stream?
3. **Single-worker broadcaster.** In-process `asyncio` pub/sub is proposed, with
   Postgres `LISTEN/NOTIFY` documented as the scale-out path. Acceptable for the
   assessment's single-worker `docker compose` deployment?
