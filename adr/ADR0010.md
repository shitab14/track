# ADR0010: Meeting Summary Snapshot & Historical Immutability

## Status
Accepted

> **Stage 1 resolution.** (1) Add the explicit attribution columns. (2) Store the
> frozen summary in `meetings.summary_snapshot`. (3) Use `APP_NOW` as the `as_of`
> for a live conclusion. All three recommendations approved.

## Context

Section 2.5 requires that, when a meeting ends, attendees see its summary —
Measurable statuses for the last closed week, Issues solved and To-Dos created
*during the meeting*, the attendees, and the rating — and that **the API returns
any ended meeting's summary, including the two seeded ones (`mt1`, `mt2`)**.
Section 2.8 asks us to explain how past summaries stay unchanged after later
edits (describing the strategy is explicitly enough).

The rules report (ADR0005, `app/domain/report.py`) already computes exactly this
per-meeting summary and is validated against the seed by `test_report`
(`mt1` scorecard week `2026-10-19`, `mt2` `2026-10-26`, `mt2` issues_solved
`["i6"]`, todos_created `["t30"]`, rating `8.3`). That logic is the answer key;
any API summary must agree with it, so we reuse it rather than re-deriving it.

Two facts complicate a naive "just recompute on request":

1. **Closed-week scores are editable** ("last save wins"), even for past weeks.
   So a past meeting's Measurable statuses would *change* if someone edits an old
   score — this is precisely the immutability risk 2.8 names. Every other input
   is already stable once a meeting ends: `solved_at`/`created_at` are historical,
   and ADR0009 forbids late joins, late ratings and further transitions after end.

2. **Clocks diverge for a live meeting.** ADR0009 stamps `started_at`/`ended_at`
   on the real wall clock (for an honest live timer), while the business world is
   frozen at `APP_NOW = 2026-11-11`. `solve_issue` (ADR0007) stamps `solved_at`
   with `APP_NOW`. For a meeting run live today, `solved_at` (Nov 11) falls
   *before* `started_at` (the real date), so the report's `[started_at, ended_at]`
   window would miss issues solved in that very meeting. The window is correct for
   the seed (all its timestamps share one clock) but not for live meetings.

## Decision

### 1. One shared summary function
Extract the per-meeting block of `generate_rules_report` into
`app/domain/summary.py::compute_meeting_summary(db, meeting, as_of_utc, solved_ids, created_ids)`
and have the rules report call it. This guarantees the API and the rules report
produce identical summaries and keeps `mt1`/`mt2` answers unchanged.

### 2. Explicit in-meeting attribution (clock-independent)
Add two nullable foreign keys, set at action time when the acting team has an
active meeting:
- `issues.solved_in_meeting_id` — set by `solve_issue` when the issue is solved
  during an active meeting.
- `todos.created_in_meeting_id` — set by `create_todo` when the To-Do is added
  during an active meeting.

"Solved/created during the meeting" is then a direct link, not a timestamp race
across two clocks. Seeded meetings carry no such link, so their summary falls
back to the report's `[started_at, ended_at]` window — exactly the computation
`test_report` already validates. This also reads as the deliberate source-linking
the brief values (2.8: how Issues and To-Dos link to their sources).

### 3. Snapshot on conclusion (immutability)
Add a nullable `meetings.summary_snapshot` (JSON) column. When a meeting ends
(advance into `ended`, or explicit end), compute the summary once with
`as_of = APP_NOW` and the attributed id lists, and store it. It is written once
and never overwritten, so later score edits cannot change a concluded meeting's
summary. `APP_NOW` is the business "now" at conclusion, which keeps a live
meeting's last-closed-week on the populated part of the seed (`2026-11-02`)
rather than a real-world date with no scores.

### 4. Serve endpoint
`GET /meetings/{meeting_id}/summary` (team read):
- If `summary_snapshot` is present, return it (immutable, app-concluded meetings).
- Otherwise compute live with `as_of = meeting.started_at` and the window-based
  solved/created lists — identical to the rules report, so seeded `mt1`/`mt2`
  are served correctly with no stored snapshot.
- A meeting that has not ended has no summary → `409`.

### 5. Clock boundaries (unchanged elsewhere)
The live section timer stays on ADR0009's real wall clock. The summary's
last-closed-week uses the business `as_of` (APP_NOW at conclusion for the
snapshot; `started_at` for the seeded fallback, both being the meeting's
business-time conclusion). "During the meeting" membership uses the explicit
links above, not a clock. No change to ADR0009's transport or state machine.

### 6. Migration, no new dependency
One Alembic revision adds `meetings.summary_snapshot`,
`issues.solved_in_meeting_id`, and `todos.created_in_meeting_id` (all nullable,
FKs `ON DELETE SET NULL`). `sqlalchemy.JSON` is used for portability across
Postgres and the SQLite test database. The seeder is unchanged; seeded rows
leave the new columns null.

## Consequences

- A concluded meeting's summary is frozen at conclusion; editing a past score
  never rewrites history. Seeded meetings recompute deterministically from stable
  historical inputs, matching the rules report.
- The API and the rules report share one implementation, so they cannot drift.
- "During the meeting" is a durable link rather than a timestamp window, so it is
  correct even though the live timer and the business clock differ.
- Cost: three nullable columns and one migration; small wiring in `solve_issue`
  and `create_todo`. ADR0009 is untouched.
- Single-meeting assumption holds: a team has at most one active meeting
  (`uq_active_team_meeting`), so attribution is unambiguous.

## Verification

Execution (next stage) should include:
- **Parity**: `test_report` still passes (shared function returns the same
  `mt1`/`mt2` values); a direct `compute_meeting_summary` test on the seed.
- **Immutability**: conclude a live meeting, capture its summary, then edit a
  closed-week score and reassert the served summary is unchanged.
- **Attribution**: an issue solved and a To-Do created during a live meeting
  appear in that meeting's `issues_solved` / `todos_created`; actions outside any
  meeting do not.
- **Seeded fallback**: `GET /meetings/mt1/summary` and `/mt2/summary` match the
  rules report values.
- **Lifecycle & authz**: active meeting → `409`; non-member → `403`.

## Stage 1 Review: Questions for User

1. **In-meeting detection.** This ADR adds explicit `solved_in_meeting_id` /
   `created_in_meeting_id` links (clock-independent, eval-friendly) rather than
   relying on the timestamp window that breaks for live meetings. Approve the two
   attribution columns, or prefer window-only with the live-clock caveat
   documented?
2. **Snapshot storage.** Store the frozen summary in a `meetings.summary_snapshot`
   JSON column captured at conclusion (true immutability), versus 2.8's
   "describing is enough" (compute-on-read only, immutability described but not
   enforced)? Recommendation: store it.
3. **`as_of` for a live conclusion.** Use `APP_NOW` (keeps the last-closed-week on
   populated seed data) as proposed, rather than the meeting's real `ended_at`
   (a real-world date with no scores)?
