# ADR0011: Frontend Architecture & Team Page

## Status
Accepted

> **Stage 1 resolution.** (1) Stack approved: React Query + shadcn/ui +
> react-hook-form/zod. (2) The two endpoints (`GET /auth/users`,
> `GET /teams/{id}/members`) and the last-closed-week completion-rate fix land in
> this ADR. (3) Team page is client-rendered. All recommendations approved.

## Context

Section 2.5 defines the Team Page: a header with a seeded user switcher and a
team selector, and four sections — Scorecard, Issues, To-Dos, Rocks. The
Scorecard and Issues sections are built once and **reused on the Meeting page**
(ADR0012). Section 2.7 requires that authorization is enforced on the server
("hiding a button is not authorization"); the UI only reflects it. The
evaluation weights Usability (15%) and Frontend code quality (10%), explicitly
valuing "organized, typed code with server state, live updates and forms handled
coherently."

The frontend is currently an ADR0000 scaffold: Next.js 14 (App Router),
TypeScript, Tailwind, `clsx`/`tailwind-merge`/`lucide-react`, and a working
`apiRequest` client that already speaks the `{code, message, data}` envelope,
supports a timeout and injects the `X-User-Id` header. No component library,
server-state layer, or pages beyond the health screen exist yet.

The backend (ADR0006–0010) already exposes everything the Team page reads and
writes:

| Need | Endpoint |
| --- | --- |
| Current user | `GET /auth/me` |
| Accessible teams | `GET /teams` (returns `user_role`) |
| Scorecard | `GET /teams/{id}/scorecard`; `POST /teams/{id}/scores`; `POST /scores/{score_id}/make-issue` |
| Issues | `GET /teams/{id}/issues`; `POST /teams/{id}/issues`; `PATCH /issues/{id}/priority`; `POST /issues/{id}/solve`; `POST /issues/{id}/todos` |
| To-Dos | `GET /teams/{id}/todos`; `POST /todos/{id}/done`; `POST /todos/{id}/undo` |
| Rocks | `GET /teams/{id}/rocks` |

Two capabilities the UI needs have **no endpoint yet**, and one existing
endpoint disagrees with the spec; these are addressed in the decision.

## Decision

### 1. Libraries (minimal, idiomatic)
- **shadcn/ui** initialized (copy-in primitives only: button, dialog, select,
  table, input, badge, tabs, dropdown-menu, progress, sonner/toast). No runtime
  UI framework dependency beyond Radix primitives shadcn pulls in.
- **TanStack React Query** for server state — caching, background refetch,
  mutations and query invalidation. This is what "server state" and "live
  updates" require; hand-rolling it would be more code and less correct.
- **react-hook-form + zod** for the modal forms (create issue, solve, add
  To-Do). Single-cell score editing uses local state, not a form.

These are the standard, lightweight choices for the required behaviors and do
not violate zero-bloat (RULE.md §3): each replaces materially more hand-written,
error-prone code.

### 2. App structure (App Router, client-rendered)
Because the "current user" is a client-side simulation (the `X-User-Id` header)
and the page needs live refetch, the Team page renders on the client.
- `Providers` (client): `QueryClientProvider` + `UserProvider` (selected seeded
  user id, persisted to `localStorage`, default `u1`) + `<Toaster/>`.
- Routes: `/` redirects to `/teams/{firstAccessibleTeam}`; `/teams/[teamId]` is
  the Team page. The Meeting route is reserved for ADR0012.
- **Header** (persistent): user switcher (dropdown of seeded users) and team
  selector (accessible dropdown of `GET /teams`). Switching user resets the team
  to the first accessible one and invalidates all queries; switching team
  navigates to its route.

### 3. Data layer
A thin set of typed hooks over the existing `apiRequest`, each injecting the
current user id from `UserProvider`: `useMe`, `useTeams`, `useScorecard`,
`useIssues`, `useTodos`, `useRocks`, and mutation hooks (`useSaveScore`,
`useMakeIssue`, `useCreateIssue`, `useSetPriority`, `useSolveIssue`,
`useAddTodo`, `useToggleTodo`). Each mutation invalidates the affected team
queries, so a change is reflected immediately in the single client (the
cross-browser live sync is the Meeting page's concern, ADR0012). Typed response
models live in `src/types`.

### 4. Authorization reflected, not enforced
The company role comes from `GET /auth/me`. Observers get a fully read-only Team
page (no inline edit, no Make-it-an-Issue, no create/solve/priority/add-todo, no
done/undo); Admins and Team Members get the actions. This is **UX only** — the
server already enforces every rule and rejects Observer writes with 403
(ADR0006, proven by tests). The ADR records this explicitly so the gating is not
mistaken for security.

### 5. Sections (Scorecard and Issues are reusable components)
- **ScorecardSection** — 13-week grid (rows = measurables with name, owner, goal,
  unit; columns = 13 weeks ending in the current one). Each cell shows value and
  a status color (on_track / off_track / pending). Inline edit writes `POST
  /scores` (last save wins); off-track cells expose **Make it an Issue** →
  `POST /scores/{id}/make-issue` with a toast, then issues refetch.
- **IssuesSection** — tabs for Unsolved (issue order) and Solved. Unsolved rows
  show title, owner, priority, created time, source measurable+week, with
  create/set-priority/solve/add-To-Do actions; Solved rows show solved time and
  note.
Both take a `readOnly` flag and a `teamId`, so ADR0012 can drop them into the
Meeting page unchanged.
- **TodosSection** — title, owner, due date, done time, source issue; overdue
  flagged; the last closed week's completion-rate widget (target 90%);
  done/undo toggle.
- **RocksSection** — read-only; current-quarter Rocks with owner, computed
  status and a progress bar; each expands to its milestones (due date, done,
  overdue).

### 6. Two new backend endpoints + one correction (small)
The frontend ADR includes the minimal backend work it depends on:
- `GET /auth/users` — list the nine seeded users (`id`, `name`, `role`) for the
  switcher. The switcher is the spec's sanctioned stand-in for login.
- `GET /teams/{id}/members` — the team's Admins and Team Members, the only valid
  owners for a new To-Do (spec 2.5). Read-access gated.
- **To-Do completion rate**: `GET /teams/{id}/todos` currently returns the
  *current* week's rate, but 2.5 asks for the *last closed* week's. Correct the
  service to the last closed week (one-line clock change, covered by a test).

### 7. UX details
Loading skeletons, empty and error states, and `sonner` toasts on every
mutation. Optimistic updates for the snappy toggles (score save, done/undo),
rolled back on error. Last-save-wins on scores is intentional; lost-update
protection is a Part 3 bonus, out of scope here.

## Consequences

- Scorecard and Issues exist once and are reused by the Meeting page, avoiding
  divergence.
- React Query gives correct caching/refetch and a clean mutation story; the Team
  page updates live within a client without bespoke state plumbing.
- Three small, well-scoped backend changes land with the frontend rather than
  leaking UI concerns into guesswork.
- Client rendering keeps the user simulation and live refetch simple; SEO/SSR is
  irrelevant for this authenticated tool. Tradeoff: no server-rendered first
  paint (acceptable here).
- Meeting real-time UI, the agenda/timer and ratings remain ADR0012.

## Verification

- Manual walkthrough of the core journey (switch user, pick team, edit a score,
  Make it an Issue, create/solve an Issue, add and complete a To-Do, expand a
  Rock) across an Admin, a Team Member and an Observer.
- Observer sees no action controls and any forced write is refused by the server.
- `npm run build` and `npm run lint` pass; components are typed against
  `src/types`.
- Backend additions get unit/endpoint tests (users list, team members list,
  corrected last-closed-week completion rate). The full Playwright core-journey
  and multi-browser meeting test remain ADR0013.
