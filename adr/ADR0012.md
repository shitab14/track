# ADR0012: Meeting Page & Real-Time Facilitation UI

## Status
Accepted

> **Stage 1 resolution.** (1) Client-side countdown re-synced from snapshots.
> (2) Conclude reuses the To-Dos section live; the exact in-meeting list is in the
> end summary (no live snapshot change). (3) Add a "Meeting" button to the Team
> page header. All recommendations approved.

## Context

Section 2.5 defines the Meeting page: the Level 10 agenda (Scorecard 5m → IDS
60m → Conclude 10m) with a section timer and an attendee roster; the Scorecard
and IDS steps **reuse the Team page sections** with all their actions; Conclude
shows the meeting's new To-Dos and ratings. One Admin or Team Member starts and
becomes facilitator; anyone who can read the team may join; only the facilitator
advances or ends, at any time. Everyone sees the same section and timer, changes
reach all attendees within ~1s, the server owns the timer, an overrun shows as
over time without advancing, and late joins / refreshes / reconnects get current
state. At the end, attendees see the immutable summary.

The backend is already built: ADR0009 provides the SSE stream and the
start/join/advance/end/rate endpoints with a `meeting_state` snapshot and
`data_changed` signals; ADR0010 provides `GET /meetings/{id}/summary`. ADR0011
built `ScorecardSection` and `IssuesSection` as reusable, `readOnly`-aware
components backed by React Query, plus the user/team context and the hook
pattern. This ADR is **frontend-only** — it consumes those.

Relevant contracts:
- `GET /meetings/{id}/events?user_id=` (SSE): named events `meeting_state`
  (full snapshot) and `data_changed` (`{scope: "scorecard"|"issues"|"todos"}`).
- Snapshot fields: `section`, `section_started_at`, `section_budget_seconds`,
  `server_now`, `over_time`, `facilitator_id`, `attendees[]`, `ratings{values,
  count, average}`, `started_at`, `ended_at`.
- `POST /teams/{id}/meetings` (start), `GET /teams/{id}/active-meeting`,
  `POST /meetings/{id}/join|advance|end`, `PUT /meetings/{id}/rating`,
  `GET /meetings/{id}/summary`.

## Decision

### 1. Real-time via EventSource, one subscription hook
A `useMeetingStream(meetingId, teamId)` hook opens an `EventSource` to the SSE
endpoint (user id as query param, since `EventSource` cannot set `X-User-Id`),
listens for the two named events, and:
- `meeting_state` → stores the latest snapshot in React state (the page's source
  of truth for section, timer, roster, ratings);
- `data_changed` → invalidates the matching React Query key (`scorecard` /
  `issues` / `todos` for this `teamId`), so the **reused sections refetch** and
  every browser converges.
`EventSource` auto-reconnects; the server's snapshot-on-connect re-syncs state on
every (re)connection, covering late joins, refreshes and facilitator reconnects
with no special handling. The hook closes the stream on unmount.

### 2. Route and lifecycle
Route `/teams/[teamId]/meeting`:
- Resolve the active meeting via `GET /teams/{id}/active-meeting`.
- **None active** → a start screen: Admins/Team Members see "Start Level 10
  Meeting" (`POST /teams/{id}/meetings`); Observers see "No active meeting".
- **Active** → `POST join` (idempotent) once, open the stream, render the
  meeting view driven by the snapshot.
- **Ended** (`section === "ended"`) → the summary report.
A "Meeting" button in the Team page header links here.

### 3. Timer bar + section navigator (server owns time, client renders it)
From the snapshot's `section_started_at`, `section_budget_seconds` and
`server_now`, the client computes a clock offset and ticks a local countdown each
second, re-synced on every snapshot — a smooth timer without per-second server
traffic (ADR0009 decision 7). Past budget it shows **over time** (and never
auto-advances). The navigator shows the three agenda steps with the active one
highlighted. The **facilitator** (`facilitator_id === userId`) sees **Advance**
and **End**; everyone else sees the agenda read-only.

### 4. Body reuses the Team sections
- **scorecard** → `ScorecardSection` (inline edit + Make it an Issue).
- **ids** → `IssuesSection` (create/priority/solve/add-To-Do).
- **conclude** → the Conclude panel (decision 5).
`readOnly` is `role === "observer"`. Because these sections use the same mutation
hooks as the Team page — which emit `data_changed` server-side — an edit in one
browser refetches in all of them, satisfying the ~1s live-sync requirement.

### 5. Conclude: roster recap + live rating
Conclude shows the To-Dos section (the meeting's follow-ups) and a **rating
interface**: an attending Admin/Team Member picks 1–10 (`PUT rating`) and may
change it until the end; the snapshot's `ratings.values[userId]` drives the
current selection and `ratings.average`/`count` the live tally. Observers cannot
rate (control hidden; server enforces). The facilitator ends the meeting here.

### 6. Attendee roster
Always visible, from `snapshot.attendees`, with the facilitator marked. It
updates live as people join (join publishes a fresh snapshot).

### 7. End → immutable summary
On `ended`, fetch `GET /meetings/{id}/summary` and render it: the last closed
week's Measurable statuses, Issues solved and To-Dos created during the meeting,
attendees and the rating. Attendee/measurable ids are enriched with names from
the final snapshot and the scorecard query where available. This is the frozen
snapshot from ADR0010, so it does not change afterward.

### 8. No backend change
Everything needed exists. The live Conclude shows the current To-Dos section;
the authoritative "created during the meeting" list is the end summary (we do not
add in-meeting todo/issue ids to the live snapshot).

## Consequences

- Scorecard and Issues exist once and are driven live inside the meeting with no
  duplication; `data_changed` ties their mutations to cross-browser refetch.
- State lives in the snapshot the server pushes, so every recovery case is one
  path and the client never computes authority it shouldn't.
- The timer is smooth yet server-authoritative; overrun is visible and never
  auto-advances.
- The two-browser Playwright proof of live sync (facilitator advances, second
  browser follows) is ADR0013 and will drive this UI.
- Frontend-only; no migration or endpoint changes.

## Verification

- Manual two-browser check: a facilitator and an attendee (and an Observer) in
  one meeting — advancing the agenda, editing a score, making/solving an Issue,
  adding a To-Do, rating in Conclude, and ending — all reflected in both browsers
  within ~1s; the Observer sees everything read-only and cannot rate.
- Reconnect/late-join: refresh mid-meeting restores the current section, timer
  and roster.
- `npm run build` (type-check + lint) passes.
- The automated two-browser Playwright test is owned by ADR0013.

3. **Entry point.** Add a "Meeting" button to the Team page header linking to the
