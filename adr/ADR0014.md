## Context

Part 3 requires the submission to ship as: a public repo with a README (≤2
pages) covering setup, the test command, assumptions, known limitations and AI
usage; the working app started with `docker compose up`; the already-committed
`rules_report.json` and its documented command; a one-page decision record
covering §2.8; and a ≤7-minute video of the core journey with two browsers in a
meeting plus the main decisions.

Current state: `docker-compose.db.yml` runs only Postgres; local runs use the
`scripts/*.sh` runners. There are no Dockerfiles, no root `README.md`, and no
decision record. Everything the app needs exists — `backend/requirements.txt`
lists all deps, the seeder is idempotent (ADR0003), migrations are Alembic, and
the rules report command is committed (ADR0005). The seeder resolves
`seed.json` from `<repo-root>/task_resources/seed.json`
(`Path(__file__)...parent*4 / "task_resources" / "seed.json"`), which the
container image must preserve.

This ADR is packaging + documentation only; no application behaviour changes.

## Decision

### 1. Full-stack `docker compose up`
Add a top-level `docker-compose.yml` (the default file) with three services, so
`docker compose up` starts the whole stack with seed data loaded:
- **db** — `postgres:16-alpine`, healthcheck, named volume (mirrors the existing
  db-only file, which is kept for the independent DB runner).
- **backend** — built from `backend/Dockerfile`; `depends_on: db (healthy)`; an
  entrypoint runs `alembic upgrade head`, then the idempotent seed, then
  `uvicorn ... :8000`. Env: `DATABASE_URL` (→ `db` service), `APP_NOW`
  (`2026-11-11T15:00:00Z`), CORS allowing `http://localhost:3000`.
- **frontend** — built from `frontend/Dockerfile`; `next build` + `next start`
  on `:3000`, with `NEXT_PUBLIC_API_URL=http://localhost:8000/api/v1` baked at
  build time (the browser, on the host, reaches the backend at `localhost:8000`).

### 2. Backend image preserves the repo layout for `seed.json`
The backend image build context is the **repo root**; the Dockerfile copies both
`backend/` and `task_resources/` into `/app/...`, and `WORKDIR /app/backend`, so
the seeder's relative path resolves unchanged — **no code change**. (Alternative
considered: a `SEED_FILE` env override; rejected to avoid touching tested code
for a packaging concern.)

### 3. Idempotent, re-runnable startup
The seed runs on every backend start and is safe to re-run (ADR0003), so
`docker compose up` a second time does not duplicate data. `docker compose down`
(without `-v`) keeps the volume; `-v` resets it. This is documented.

### 4. Root `README.md` (≤2 pages)
Covering, tightly:
- **What it is** and the stack.
- **Run**: `docker compose up` → frontend `:3000`, API docs `:8000/docs`.
- **Test**: `./scripts/test_all.sh` (one-time `npx playwright install chromium`).
- **Rules report**: the documented command and `rules_report.json`.
- **Assumptions** (the judgement calls): two clocks (wall-clock live timer vs
  frozen `APP_NOW` business rules; summary "last closed week" uses `APP_NOW` at
  conclusion); Scorecard shows the 13 weeks ending at the last closed week plus a
  current-week column; completion rate is the last closed week; "during the
  meeting" is an explicit attribution link; summary immutability via a snapshot
  frozen at conclusion; the user switcher is the login stand-in; SSE auth via a
  query parameter.
- **Known limitations**: in-process SSE broadcaster → single worker (scale-out =
  Postgres `LISTEN/NOTIFY`); last-save-wins on scores/priority (no lost-update
  protection — a Part 3 bonus); no audit trail; client-rendered frontend.
- **AI usage**: Claude (Claude Code) used throughout under an ADR-driven,
  two-stage human-reviewed workflow (RULE.md) — design and implementation across
  backend, frontend, tests and docs; where and how, named honestly.

### 5. One-page decision record — `DECISIONS.md`
A single page covering §2.8, summarizing and linking the detailed ADRs:
- **Data model & source links** → ADR0001/0010 (Issue→measurable+week,
  To-Do→issue, in-meeting attribution).
- **API design** → ADR0007 (REST, envelope, OpenAPI).
- **Real-time transport, ownership & recovery** → ADR0009 (SSE, DB row as truth,
  snapshot-on-connect).
- **Duplicate-free Make it an Issue under concurrency** → ADR0008 (partial unique
  index + idempotent recovery).
- **Keeping past summaries unchanged after edits** → ADR0010 (snapshot at
  conclusion; seeded recompute from stable inputs).

### 6. Video walkthrough plan — `VIDEO_PLAN.md`
A written shot-list/script for the ≤7-minute video (the recording itself is done
by the author): the core journey end to end, two browsers in one meeting
(facilitator advances, the second follows; make an Issue; solve; rate; end →
summary), and a 2-minute tour of the main decisions. Timed segments so it fits 7
minutes.

## Consequences

- A grader runs exactly one command (`docker compose up`) to get the working,
  seeded app; one command (`./scripts/test_all.sh`) to run the suite.
- No application code changes; packaging preserves the seeder's path by image
  layout.
- Building images needs Docker and a network for base images and dependency
  installs (first build is slow, then cached).
- The README, decision record and video plan complete the submission artifacts;
  only the recorded video remains a manual author step.

## Verification

- `docker compose up` on a clean checkout brings up db + backend + frontend; the
  app loads at `:3000` with seed data; `:8000/docs` serves OpenAPI; a second
  `up` does not duplicate data.
- `rules_report.json` reproduces from the documented command.
- README stays within two pages; `DECISIONS.md` within one.
